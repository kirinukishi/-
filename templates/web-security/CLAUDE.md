## セキュリティチェック（双子エージェント方式）

コードを書く・修正するたびに、以下の2つの視点で自己レビューを行うこと。

### ブラックハッカー視点（攻撃者）

書いたコードに対して、以下の攻撃が可能か徹底的に検証せよ：

- **SQLインジェクション**: ユーザー入力がクエリに直接結合されていないか
- **XSS（クロスサイトスクリプティング）**: ユーザー入力がHTMLにエスケープなしで出力されていないか
- **CSRF**: フォーム送信に適切なトークン検証があるか
- **認証バイパス**: ログインなしでアクセスできるAPIや画面がないか
- **パストラバーサル**: ファイルパスにユーザー入力が含まれていないか
- **機密情報の漏洩**: APIキー、パスワード、トークンがコードやログに露出していないか
- **オープンリダイレクト**: リダイレクト先URLをユーザーが操作できないか
- **依存パッケージの脆弱性**: 既知の脆弱性を持つパッケージを使っていないか

### ホワイトハッカー視点（防御者）

発見した問題に対して、以下の方針で修正を提案せよ：

- パラメータ化クエリの使用（SQLインジェクション対策）
- 出力時のエスケープ処理（XSS対策）
- CSRFトークンの実装
- 認証・認可ミドルウェアの適用
- 入力値のバリデーションとサニタイズ
- 環境変数による機密情報の管理（.envをgitignoreに含める）
- Content-Security-Policyヘッダーの設定
- Rate Limitingの実装

### レビュー出力ルール

コードを書いたら、変更内容の末尾に以下の形式でセキュリティレビュー結果を報告すること：

```
## セキュリティレビュー
- [x] SQLインジェクション: 問題なし（パラメータ化クエリ使用）
- [!] XSS: 修正済み（出力エスケープを追加）
- [x] 認証: 問題なし
- ...該当する項目のみ記載...
```

## 禁止事項

- .env ファイルをGitにコミットしない
- APIキーやシークレットをソースコードに直接書かない
- eval() を使わない
- innerHTML に未サニタイズのユーザー入力を渡さない
- HTTPSなしで認証情報を送信する設計にしない
